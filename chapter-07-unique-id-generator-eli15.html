Scene 01 · 晚上 8:00 限量開賣

小明按下購買，誰替這筆訂單取名字？

這個「名字」會一路跟著付款、出貨、退款與客服。它不能只在畫面上看起來不重複，而是幾年後還要準確指向同一筆資料。

Temporary ID：先把畫面顧好

它只要在這次操作裡不撞名，讓 optimistic UI、cache key 與錯誤重試知道「是哪一列」即可。

Permanent ID：把所有資料接起來

訂單、付款、物流、發票、客服單與稽核紀錄，都靠它確認自己談的是同一筆交易。

先猜猜看：直接用現在的訂單總數加 1，可以嗎？

只有一台資料庫時通常可以，而且是很好的選擇。真正的麻煩要等到很多台伺服器同時接單才出現。

Scene 02 · 十秒湧入一萬筆訂單

為什麼多幾台伺服器，流水號反而變難？

限量商品開賣時，一台伺服器吃不下所有請求。Load Balancer 會把買家分給 A、B、C 三台 Order Server。

123…10k
Load Balancer
Order Server A
Order Server B
Order Server C
order 101 order 101 order 101

如果每台伺服器都只看自己的記憶體，三台都可能以為「下一號是 101」。唯一 ID 的第一個難題不是數字怎麼加，而是分散的機器怎麼避免使用同一個號碼空間。

先猜猜看：撞號最壞只是資料庫報錯嗎？

報錯反而是比較安全的結果。若資料模型或整合流程沒有及時擋住，可能發生：

  • 付款紀錄連到另一位買家的訂單。
  • 客服查 101，拿到錯誤的收件地址。
  • 物流事件覆蓋別人的出貨狀態。

所以永久 ID 至少要做到：不同機器不重複、產生速度夠快，而且加伺服器時不用每筆請求都先開會。

Scene 03 · 我們試了四種發號方式

每個方法都解一題，為什麼還不夠？

沒有一種 ID 永遠最好。下面每次嘗試都值得用，只是它們適合的系統大小與限制不同。

1

Database auto increment

所有訂單交給同一台資料庫加一：101、102、103。它簡單、短、好查。

但所有寫入都依賴同一個發號點；跨資料庫或跨區後，它會變成瓶頸與單點。

仍然適合：
單一資料庫的小型後台。
2

多主奇偶號

DB A 發奇數，DB B 發偶數，兩邊可以同時工作，也不會重複。

加第三台時要重排規則；而且號碼大小不再可靠代表全域建立順序。

解到：
兩個固定發號點分流。
3

UUIDv4

每台伺服器都能自己產生一長串隨機 ID，不必詢問中央服務。

它是 128-bit、主要為隨機資料；不符合這次「精簡 64-bit、能大致按時間排」的需求。

仍然適合：
重視本地產生與不透明 ID。
4

Ticket Server

架一個專門發號的中央服務，所有 Order Server 都向它領取短而有序的號碼。

訂單又要排隊等同一個服務；做成多台高可用後，發號機彼此還是要協調範圍。

解到：
統一發出短、有序的 ID。

我們真正缺的組合

像 UUID 一樣能在本機產生，像資料庫 ID 一樣精簡，又能讓新資料大致排在舊資料後面，而且不必每筆訂單都去中央服務領號。

先猜猜看：能不能把「時間」直接放進 ID？

可以，但只放時間還不夠。同一毫秒可能有多台機器、每台又收到多筆訂單，因此還需要「機器身分」與「同毫秒序號」。

Scene 04 · 把答案寫進 ID 本身

Snowflake 怎麼讓三台機器各自發號？

把它想成包裹標籤：不是只寫流水號，而是同時記下「何時處理、哪條產線處理、這一瞬間的第幾件」。

ORDER ID LABEL 64-BIT / INTERNAL
WHEN 20:00:00.120
WHERE 台北 / Server 7
WHICH ONE 同毫秒第 2 筆
0 1 bit
timestamp 41 bits
datacenter 5 bits
machine 5 bits
sequence 12 bits
時間：讓新資料大致排在後面

同一台機器進入新的毫秒時，sequence 會重新從 0 開始。

例：20:00:00.120

1 + 41 + 5 + 5 + 12 = 64 bits。其中 datacenter 與 machine 合起來就是 node identity：32 個機房 × 每個機房 32 台機器，共 1,024 個生成節點。12-bit sequence 則提供同一節點、同一毫秒內 0 到 4,095，也就是 4,096 個位置。

這不是完全不協調。部署時仍要替每台生成器分配不重複的 node identity；只是協調從「每一筆訂單」降成「機器加入或離開時」。

先猜猜看：兩台機器同一毫秒都用 sequence 0，會撞號嗎？

不會，只要它們的 datacenter / machine 組合不同。完整 ID 比的是所有欄位，不是只看 sequence。

Scene 05 · 現實世界不會永遠照劇本走

時鐘倒退或一毫秒太忙，會發生什麼？

Snowflake 把中央服務的壓力拆給每個節點，也把責任一起拆過去：每台機器必須管好自己的時間、身分與序號。

現實狀況 可能後果 安全處理
Clock rollback 20:00:00.500 校時後變成 20:00:00.480，可能回到用過的 timestamp / sequence 範圍。 倒退很小可等待；倒退較大就拒絕發號、告警並把流量導到健康節點。
Sequence exhaustion 同一節點、同一毫秒來到第 4,097 筆。若直接從 0 重來，就會重複先前組合。 等下一毫秒或回傳過載，讓上游分流；不能安靜繞回 0。
Duplicate node identity Server A、B 都拿到 datacenter=3, machine=7，兩台進入相同 ID 空間。 用租約或配置中心分配身分，啟動時發現衝突就拒絕上線。

前端最容易踩到的坑

Snowflake 可能大於 JavaScript Number 的安全上限 2^53 - 1。API 應以字串傳輸，前端也保持字串；不要為了排序或顯示先轉成 Number。

{
  "id": "1541815603606036480"
}

另外，Snowflake 會透露大致建立時間，也有規律可循。知道 ID 不代表有權讀取資料；授權必須另外檢查，公開網址也可以使用另一個不透明 ID。

Scene 06 · 把技術放回產品決策

四種真實情境，你會選哪一種 ID？

先看系統需要什麼，再選最簡單的方案。Snowflake 是一種答案，不是每一題的答案。

QUESTION 01

公司內部後台，只有一台主要資料庫，每天建立幾百筆資料。

查看建議

選資料庫 auto increment。單一資料庫、小流量時它簡單可靠，不需要額外管理時鐘與節點身分。

QUESTION 02

離線筆記 App 沒網路時也要建立資料，幾天後才同步。

查看建議

選 UUIDv7 或 ULID，讓裝置離線時自行產生。不過 ID 不撞號，不代表兩台裝置同時改同一篇筆記就能自動合併。

QUESTION 03

大量訂單與事件分散寫入，需要精簡 64-bit ID，也想大致按時間排。

查看建議

選 Snowflake，因為題目明確要求 64-bit、高吞吐與時間趨勢；同時接受管理時鐘與節點身分的維運成本。

QUESTION 04

公開訂單網址不能讓別人猜到建立時間或交易量。

查看建議

保留 Snowflake 作內部主鍵，另外產生不可推測的 public ID。無論 ID 長什麼樣，API 都還是要檢查使用者有沒有權限。

先問「誰要產生、能不能連網、格式多大、要不要排序、能不能透露時間」，再選最簡單的 ID。不要先選 Snowflake，再替它找理由。
