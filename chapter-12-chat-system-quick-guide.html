先看規模

聊天系統・十分鐘快速版

第十二章快速導覽・給前端工程師的系統設計讀書會

聊天跟動態牆最大的差別是「即時」：A 送出的那一刻，B 就要看到。同時還要永久保存紀錄、多裝置看到同一份對話，所以連線數才是真正的瓶頸，不是每秒訊息數。

[A] 傳訊息 → [聊天伺服器] → 存起來 → [B 在線？]
                                      ├─ 是 → WebSocket 推給 B
                                      └─ 否 → 推播通知

書中的需求：一對一與小群組（上限 100 人）、5,000 萬 DAU、純文字、紀錄永久保存、多裝置、手機與網頁。

書中的數字意義
5,000 萬 DAU需求設定的規模
100 萬並發使用者 × 每條連線約 10 KB全部連線約 10 GB 記憶體，理論上單機放得下（書中說很粗略）
Facebook 與 WhatsApp 合計每天約 600 億則感受訊息量級

書中沒有給每秒訊息數或儲存量的推算，所以這裡不自己編數字。

🏗️ 你負責 App 的「訊息」分頁。使用者預期對方送出的瞬間就看到，換手機登入也要看到同一份對話。

一句話：書中只粗估 100 萬連線約 10 GB 記憶體，但提醒不能把所有連線放在一台，單點故障才是最大問題。

現在的問題

HTTP 只能客戶端發問，伺服器要怎麼主動把訊息推給 B？

發送端用 HTTP 沒問題；難的是接收端。書中比較三種做法：

做法運作方式問題
輪詢定時問「有新訊息嗎？」多半是空回應，間隔長又不即時
長輪詢伺服器扣著請求，有訊息才回收發兩端可能連到不同伺服器；逾時要重連
WebSocket一條持久的雙向連線連線要長期維持，伺服器需管理狀態

WebSocket

客戶端先發 HTTP 請求要求升級協定，之後同一條連線改成雙向傳輸。使用 80 或 443 埠，能穿過多數防火牆。收發共用同一條連線，設計最單純。

代價

連線不斷開，伺服器不再是「請求完就忘記」。同時在線的人數決定要幾台機器。

🏗️ 你寫過 setInterval(() => fetch('/messages'), 3000)。使用者一多，伺服器就被「有新的嗎？」淹沒。

一句話：要即時又頻繁收發，用 WebSocket；更新少、使用者少時，輪詢就夠了。

現在的問題

連線一直開著，使用者該連哪一台聊天伺服器？

書中把服務分三類：登入、註冊、個人資料這類無狀態服務放負載平衡後面；聊天服務是有狀態的，每個客戶端黏在一台伺服器上；推播則是第三方整合。

服務發現（Service Discovery）

  1. 使用者登入，經負載平衡到 API 伺服器。
  2. 驗證後，服務發現依地理位置、伺服器容量挑一台聊天伺服器，回傳給客戶端。
  3. 客戶端與它建立 WebSocket 連線。

代價

要多維護一個服務發現元件（書中以 Apache Zookeeper 為例）。聊天伺服器掛掉時，它也要負責分配新的伺服器，客戶端再重連。

🏗️ 一般 API 像丟一張紙條就走；WebSocket 像打一通不掛斷的電話，總機必須記得這個人接在哪一條線。

一句話：有狀態的是聊天伺服器，它要知道誰連在自己這裡；服務發現決定誰連哪一台。

現在的問題

連線有了，海量的聊天紀錄要存在哪裡？

使用者資料、設定、好友名單量不大，放關聯式資料庫，用複寫與分片擴展。聊天歷史量極大、只增不減，而且多數人只看最近的訊息，偶爾跳回很久以前。

聊天歷史用 KV 儲存

容易水平擴展、讀取延遲低。關聯式資料庫的索引在長尾資料的隨機存取上很吃力。業界實例：Facebook 用 HBase，Discord 用 Cassandra。

訊息 ID 要夠用

ID 必須唯一且能依時間排序。KV／NoSQL 沒有 auto_increment；created_at 可能撞時間。做法是 Snowflake 這類全域序號，或只在單一對話內唯一的區域序號，順序只在同一個對話內有意義，區域序號更簡單。

一句話：歷史訊息放 KV；message_id 同時決定順序，也是後面多裝置同步的書籤。

現在的問題

一則訊息從 A 到 B 怎麼走？換新手機又怎麼補訊息？

[A] 傳訊息
 ↓ 1. 到聊天伺服器 1
 ↓ 2. 向 ID 產生器取得 message_id
 ↓ 3. 送進訊息同步佇列
 ↓ 4. 存進 KV 儲存
 ├─ B 在線 → 5a. 轉到 B 的聊天伺服器 2 → 6a. WebSocket 推給 B
 └─ B 離線 → 5b. 推播通知伺服器發推播

多裝置與小群組

多裝置：每台裝置記錄 cur_max_message_id，同步時取回「接收者是自己、ID 比它大」的訊息。

小群組：寫擴散。訊息複製到每位成員的同步佇列，每人像有自己的收件匣，讀取簡單。

代價

群組越大，複製份數越多。書中以微信為例，群組上限 500 人，因為這做法不適合大群組。這跟第十一章的 Fanout on write 是同一個取捨：讀取簡單，寫入放大。

🏗️ 手機的 cur_max_message_id 是 50，網頁是 42。網頁登入時只要補 43 以後的訊息。

一句話：ID 可排序，所以能當同步書籤；收件匣模式把群組變成「每人讀自己的佇列」。

現在的問題

好友名單旁那顆綠點，怎麼知道對方在不在線上？

登入時狀態設為 online 並記錄 last_active_at，登出時設為 offline。但手機進電梯、網路瞬間中斷，不代表使用者登出；一斷線就變離線，綠點會一直閃。

心跳 + 發布／訂閱

在線的客戶端每隔幾秒（例如 5 秒）送一次心跳；超過設定時間（例如 30 秒）沒收到才判定離線。狀態變化發布到每一對好友的頻道（A-B、A-C…），好友各自訂閱，就收到通知。

代價

逾時太短會閃爍，太長則離開的人很久才變灰。群組若有十萬人，一次狀態變動要通知十萬人，成本太高。書中建議大群組只在進入群組或手動刷新時才查狀態。

一句話：心跳加逾時，區分「暫時掉線」與「真的離開」；大群組別主動推狀態。

收尾

核心流程都有了，面試還有時間可以談什麼？

  • 多媒體：圖片、影片的壓縮、雲端儲存、縮圖。
  • 端對端加密：本章不要求，實際產品常需要。
  • 客戶端快取：減少與伺服器之間的資料傳輸。
  • 載入速度：例如 Slack 的地理分散快取網路 Flannel。
  • 錯誤處理：聊天伺服器故障時由服務發現分配新的伺服器；訊息重送靠重試與佇列。

自我檢查

用自己的話解釋看看

使用者說「對方畫面上的訊息順序跟我這邊不一樣」，為什麼用 created_at 排序有風險？

兩則訊息可能在同一時間建立，各裝置的時間也有誤差，無法確定先後。應使用可排序的訊息 ID（全域序號或頻道內序號）。

使用者搭電梯斷線 10 秒，綠點閃了一下，該怎麼調整？

心跳逾時要大於一般短暫斷線的時間，例如 30 秒。太短會閃爍，太長則真的離開的人會延遲很久才顯示離線。

WebSocket 斷線重連後漏了幾則訊息，前端要記什麼才補得回來？

記錄目前看到的最大 message_id，重連後向伺服器要 ID 比它大的訊息。
