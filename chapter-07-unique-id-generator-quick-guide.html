先建立熟悉的模型

Unique ID Generator 十分鐘快速版

第七章快速導覽・給第一次接觸分散式唯一 ID 生成器的前端工程師

最直覺的做法是讓資料庫自己遞增：

INSERT 一筆訂單 → 資料庫回傳 id = 101, 102, 103...

單台資料庫時完全沒問題，簡單又好懂。但當多個服務、多個分片、甚至多個機房同時要建立資料時，大家不能都排隊去問同一台資料庫要下一個號碼是多少——那台資料庫會變成全系統的瓶頸與單點。

本章要找一個能讓多台機器「各自」產生 ID，卻仍然滿足以下五個條件的方案：

需求為什麼需要
全球唯一不同機器不能產生相同 ID
64-bit 整數儲存與索引比長字串精簡
趨勢遞增新資料大致排在舊資料後面，利於索引
低延遲、高吞吐建立資料不能都卡在遠端發號服務
水平擴展加節點就能提高整體產生能力
🏗️ 使用者按下「建立訂單」時，前端會先用一個 temporary ID（例如 temp_abc123）更新畫面，等後端回傳 permanent ID 才替換掉。這兩種 ID 責任完全不同：temporary ID 只要畫面上不撞名，permanent ID 卻要在跨機房、多年後仍唯一指向同一筆資料。

現在的問題

所有寫入依賴同一個發號點，該怎麼分散？

幾種直覺方案輪流嘗試，卻總是少一塊：

多主資料庫各自遞增

兩台資料庫各自設定不同起點、步長都是 2：DB A 發 1, 3, 5...；DB B 發 2, 4, 6...，不會重複。

代價

新增第三台要把步長全部改成 3；而且號碼大小不再代表真正的建立時間先後。

UUIDv4

每台機器自己產生，正確使用時碰撞機率極低，完全不用問中央服務。

代價

128-bit，超過本題限制；內容隨機，無法依 ID 排時間，也拖累有序索引的效能。

Ticket Server（集中發號服務）

應用伺服器改向一個專門的中央服務領號，號碼短、有序。

代價

中央服務本身還是瓶頸；部署多台高可用後，又要協調彼此的號碼範圍。

一句話：每個方案都在「不用中央協調」「64-bit」「趨勢遞增」三者中至少放棄一項——我們缺的是能同時滿足三者的組合。

現在的問題

怎麼讓每台機器不必逐筆協調，就能各自產生唯一 ID？

Snowflake 的想法是：把「時間、機器身分、同一瞬間的順序」直接編進 ID 本身，機器只要知道自己是誰、現在幾點，就能獨立組出答案。

🏗️ 物流包裹標籤同時記錄「哪天處理、哪個物流中心、哪條產線、這一秒的第幾件」。只要物流中心與產線編號不重複，寄件時完全不用打電話問總公司下一號是多少。

把 64 bits 切成四段

 1 bit    41 bits         5 bits      5 bits     12 bits
┌────┬────────────────┬───────────┬───────────┬────────────┐
│ 0  │ timestamp (ms) │ datacenter│  machine  │  sequence  │
└────┴────────────────┴───────────┴───────────┴────────────┘
  1. 1 bit：固定 0，維持非負整數。
  2. 41 bits：現在時間減自訂起點（Custom Epoch），約可用 69.7 年。
  3. 5 + 5 bits：32 個機房 × 32 台機器 = 1,024 個生成節點。
  4. 12 bits：同一台機器、同一毫秒內的序號，0～4,095。

代價

Bit 分配不是固定答案：節點少但單機流量高，就該把 node bits 讓給 sequence。每個欄位都要先算節點數、峰值吞吐與系統壽命再決定。

⚠️ 前端注意：JavaScript Number 只能安全表示到 2^53 - 1，API 通常把 Snowflake ID 當字串傳回，不要轉成 Number；組合或運算 ID 要用 BigInt。

一句話：Snowflake 把「誰、何時、第幾個」都塞進 64 bits，機器只要管好自己的欄位，就不必逐筆問中央要號碼。

現在的問題

知道每段放什麼，生成器要怎麼實際運作？

每個生成程序記住兩個狀態：lastTimestamp（上次用過的毫秒）與 sequence（該毫秒已發到第幾號）。這兩個狀態的讀取與更新必須串行或原子化，否則並行請求可能拿到相同 sequence。

收到請求時的三條路

currentTimestamp > lastTimestamp
  → 進入新的一毫秒，sequence 歸零

currentTimestamp = lastTimestamp
  → sequence + 1
  → 超過 4,095 就等下一毫秒或回傳過載

currentTimestamp < lastTimestamp
  → 時鐘回撥，進入保護流程，不能照常產生

代價

不是完全零協調：部署時仍要分配不重複的 datacenter / machine，只是協調頻率從「每一筆 ID」降成「節點變動時」才需要一次。

例如節點位於 datacenter=3, machine=7，同一毫秒收到三個請求：

請求 A：timestamp=T,   dc=3, machine=7, sequence=0
請求 B：timestamp=T,   dc=3, machine=7, sequence=1
請求 C：timestamp=T,   dc=3, machine=7, sequence=2
下一毫秒：timestamp=T+1, dc=3, machine=7, sequence=0

另一台 machine=8 即使同時從 sequence 0 開始，machine 欄位不同，完整 ID 依然不會重複。

一句話：Snowflake 只保證「趨勢遞增」，不是嚴格連號；時鐘差異與 node bits 都會影響順序，不能當跨節點的精確排序。

現在的問題

拿掉中央協調後，換來每個節點要對自己的時間與身分負責

三個實際邊界

  1. 時鐘回撥：NTP 校時或機器搬移可能讓系統時間比 lastTimestamp 小，若直接沿用，可能重複發出已用過的 timestamp + sequence。
  2. sequence 用完：同一毫秒內第 4,097 個請求不能安靜繞回 0，否則撞號。
  3. 節點身分重複：兩台機器誤用相同 (datacenter, machine)，會共用同一個 ID 空間。

代價

處理方向都要在「延遲」與「可用性」之間取捨：小幅回撥可以等待，大幅回撥該直接拒絕產生並告警，比事後修復重複 ID 便宜得多。

問題可能後果處理方向
時鐘回撥撞號、排序倒退短暫等待、拒絕服務、受保護邏輯時間
sequence 耗盡同毫秒內撞號等下一毫秒或回傳過載，不可歸零
節點身分重複不同節點共用命名空間唯一分配、租約、啟動衝突檢查

一句話：ID 也不是安全憑證——Snowflake 的 timestamp 可被解析，若不能透露時間或業務量，要另外提供不透明的 public ID。

現在的問題

如果不受 64-bit 限制，還有其他選擇嗎？

現在也有標準化、可排序、不必管理 machine ID 的方案：

UUIDv7 / ULID

UUIDv7：128-bit，高位放 Unix 毫秒時間，其餘保留 UUID 生態相容性。
ULID：128-bit，前 48 bits 是時間，26 個字元、字典序可排序，適合日誌與 URL。

代價

都不需要 machine ID，但也都不是 64-bit；同一毫秒是否單調仍取決於生成器實作，不能當成跨節點的嚴格順序。

方案大小時間排序管理節點 ID適合情境
Snowflake64-bit 整數趨勢遞增要精簡、高吞吐的內部主鍵
UUIDv7128-bit UUID時間高位不要標準 UUID、跨語言生態
ULID128-bit、26 字元字典序不要可讀文字、日誌與 URL

一句話：64-bit 是硬限制才選 Snowflake；已有 UUID 生態選 UUIDv7；重視文字與字典序評估 ULID——先列需求，再選最簡單的格式。

自我檢查

用自己的話解釋看看

為什麼多主資料庫各自遞增，仍不能保證全域時間排序？

因為 ID 反映的是各自資料庫的數列進度，不是真實建立時間。DB A 可能先發出比 DB B 更大的號碼，雖然不會重複，但號碼大小不再等於時間先後。

Snowflake 為什麼同時需要 machine ID 和 sequence，缺一個會怎樣？

machine ID 區分同一毫秒的不同節點，sequence 區分同一節點、同一毫秒的不同請求。少了 machine ID，不同機器同毫秒可能撞號；少了 sequence，同一機器同毫秒的多筆請求就沒辦法互相區分。

時鐘回撥時，為什麼「等待」和「拒絕產生」都是合理選擇，該怎麼判斷?

回撥幅度小（幾毫秒）可以短暫等待系統時間追上，代價是增加一點延遲；回撥幅度大或狀態不明時應直接拒絕產生並告警，讓流量切到健康節點，因為重複 ID 造成的資料錯誤，通常比短暫不可用更難修復。
