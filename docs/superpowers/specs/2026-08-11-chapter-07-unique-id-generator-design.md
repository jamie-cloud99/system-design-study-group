# Chapter 07 唯一 ID 生成器講義設計

## 目的

新增第七章標準講義 `chapter-07-design-a-unique-id-generator.md`，延續本系列「問題 -> 解法 -> 新問題」的因果鏈，讓剛開始學系統設計的前端工程師理解：單機資料庫的流水號到了分散式環境為什麼不再夠用，以及 Snowflake 如何在不依賴中央服務逐筆發號的情況下產生唯一、可排序且高效的 ID。

講義以原章的方案比較與 Snowflake 設計為主線，另外用短篇幅補充 UUIDv7 與 ULID。現代方案只用來幫助實務選型，不取代原章，也不展開成另一套完整設計。

- 預計講解時間為 30 分鐘。

- 不假設讀者熟悉 UUID、Snowflake、時鐘回撥或分散式協調。

## 核心學習成果

讀完後，讀者應該能夠：

1. 說明分散式唯一 ID 的核心需求，不只回答「不能重複」。
2. 比較單一資料庫、多主資料庫、UUID、Ticket Server 與 Snowflake 的取捨。
3. 說明 Snowflake 的 64-bit ID 如何由時間、機房、機器與序號組成。
4. 根據 bit 數算出系統可運作年限、節點數與單節點產生速率。
5. 區分全球唯一、碰撞機率極低、趨勢遞增與嚴格連號。
6. 說明時鐘回撥、同毫秒序號耗盡與 machine ID 重複會造成什麼問題。
7. 在 Snowflake、UUIDv7 與 ULID 之間做出有理由的初步選擇。

## 核心思路

唯一 ID 生成器不只是把數字加一。當多台機器同時建立訂單、訊息或事件時，系統需要在不互相等待的情況下避免重複，還要考慮索引效率、排序、容量與故障。

講義會從一個最簡單的流水號開始，逐一揭露每種解法留下的限制，最後推導出 Snowflake：把一個 64-bit 整數切成數個欄位，讓每台生成節點依靠時間、自己的身分與同毫秒序號獨立產生 ID。

## 內容架構

### 1. 為什麼不能只用流水號

從訂單 ID 切入，說明前端畫面看到的 `order_12345` 背後需要滿足的條件：

- 全球唯一
- 可放進 64-bit 整數
- 趨勢遞增，方便資料庫索引與時間排序
- 低延遲、高吞吐
- 多台機器可同時產生

另外用 optimistic update 的暫時 ID 區分「前端暫時識別」與「後端永久識別」，避免讀者把兩者混為一談。

### 2. 四種候選方案與淘汰理由

依照問題演進比較下列方案：

1. **單一資料庫 `auto_increment`**：簡單且有序，但資料庫是單點與吞吐瓶頸。
2. **多主資料庫自增**：不同資料庫使用不同起點與步長，能分散負載，但擴縮設定複雜，也無法自然維持全域時間順序。
3. **UUID**：各節點可自行產生，協調成本低；傳統 UUIDv4 是 128-bit 且隨機，不符合原章的 64-bit 與趨勢遞增需求。
4. **Ticket Server**：由中央服務發出短且有序的 ID，但中央服務成為瓶頸與故障點；做成多台後又重新遇到協調問題。

本節的目的不是宣稱前三種方案永遠不能用，而是根據本章需求逐項淘汰。每個方案都要指出適合的較小場景，避免把選型寫成絕對規則。

### 3. Snowflake 64-bit 結構

以原章配置拆解：

```text
| 1 bit | 41 bits timestamp | 5 bits datacenter | 5 bits machine | 12 bits sequence |
```

- 1 bit：符號位，固定為 0。
- 41 bits：相對於自訂 epoch 的毫秒時間戳。
- 5 bits：機房 ID，最多 32 個機房。
- 5 bits：機器 ID，每個機房最多 32 台生成節點。
- 12 bits：同一台機器在同一毫秒內的序號，最多 4,096 個 ID。

講義要透過一個具體 ID 的生成過程說明各欄位如何組合，而不是只列 bit 表格。

### 4. 一個 ID 如何被產生

資料流如下：

```text
收到產生 ID 的請求
  -> 讀取目前毫秒時間
  -> 比較上一次產生 ID 的時間
  -> 同一毫秒：sequence + 1
  -> 新的毫秒：sequence 歸零
  -> 組合 timestamp / datacenter / machine / sequence
  -> 回傳 64-bit ID
```

本節用簡化流程建立心智模型，不提供可直接上線的演算法實作。需要清楚說明：唯一性依賴 machine ID 不重複、時間沒有倒退，以及同一毫秒內 sequence 不重複。

### 5. 容量與故障邊界

講義要帶讀者實際算出：

- 41-bit 毫秒時間約可使用 69 年。
- 5 + 5 bits 可識別 32 x 32 = 1,024 台生成節點。
- 12-bit sequence 讓單節點每毫秒可產生 4,096 個 ID。
- 理論單節點上限約為每秒 4,096,000 個 ID，但實際能力仍受實作與硬體限制。

必須討論三個故障情境：

- **時鐘回撥**：系統時間小於上次時間時，可能產生重複或破壞排序。講義介紹短暫等待、拒絕產生、使用邏輯時間等方向，但不指定唯一標準答案。
- **sequence 耗盡**：同一毫秒超過 4,096 筆時，等待下一毫秒或回傳過載錯誤，不能直接繞回零。
- **machine ID 衝突**：部署或服務發現機制分配到重複 ID 時，即使演算法本身正確仍會撞號，因此節點身分配置也屬於系統的一部分。

另外說明 Snowflake 只保證趨勢遞增，不保證跨節點嚴格連號，也不應把 ID 當作不可猜測的安全憑證。

### 6. 現代補充：UUIDv7 與 ULID

本節控制在短篇幅，只回答選型問題：

- **UUIDv7**：標準化的 128-bit、以 Unix 時間為基礎的 UUID，具備時間排序特性，適合想使用標準 UUID 生態且不想管理 machine ID 的系統。
- **ULID**：128-bit、可按字典序排序的文字識別碼，對日誌與人工操作友善，但是否採用要看語言套件、單調性實作與資料庫儲存方式。
- **Snowflake**：適合明確需要 64-bit 整數、高吞吐與大致時間排序，並能管理節點身分及時鐘風險的系統。

補充內容不把 UUIDv7 或 ULID 描述成 Snowflake 的全面替代品。選型表只比較長度、排序性、中央協調、節點身分管理與常見使用情境。

## 因果鏈

講義開頭的 ASCII 因果鏈固定為：

```text
單一資料庫流水號
  -> 簡單、有序
  -> 問題：單點與吞吐瓶頸

多主資料庫自增
  -> 分散負載
  -> 問題：配置複雜，難維持全域時間順序

UUID
  -> 各節點自行產生
  -> 問題：傳統 UUIDv4 太長且不按時間排序

Ticket Server
  -> 集中發出短且有序的 ID
  -> 問題：中央服務再次成為瓶頸與故障點

Snowflake
  -> 時間 + 節點身分 + 同毫秒序號
  -> 多台節點可獨立產生唯一、趨勢遞增的 64-bit ID
  -> 新問題：時鐘回撥、序號耗盡、machine ID 衝突

現代補充
  -> UUIDv7 / ULID 提供不同的排序與部署取捨
```
