Recap Hash Ring 分布不均 虛擬節點 總覽 自我檢查

先建立熟悉的模型

Consistent Hashing 八分鐘快速版

第五章快速導覽・給第一次接觸一致性雜湊的前端工程師

要把資料分散到多台伺服器，最直覺的做法是：

serverIndex = hash(key) mod N

N = 4 台伺服器時很正常：

key "user_001"  → hash = 12 → 12 mod 4 = 0 → Server 0
key "user_002"  → hash = 47 → 47 mod 4 = 3 → Server 3
key "user_003"  → hash = 30 → 30 mod 4 = 2 → Server 2

但只要一台伺服器掛掉，N 變成 3：

key "user_001"  → 12 mod 3 = 0 → Server 0 ✓（沒變）
key "user_002"  → 47 mod 3 = 2 → Server 2 ✗（原本 Server 3）
key "user_003"  → 30 mod 3 = 0 → Server 0 ✗（原本 Server 2）

N 一變，大多數 key 的目標伺服器全部跟著變。如果這些 key 是快取資料，代表大規模快取同時失效——所有請求瞬間打到資料庫，就像完全沒有快取一樣。

🏗️ 想像圖書館把書按「書名首字母 mod 房間數」分放。多開一間房，所有書的位置全部要重算、重搬——哪怕只是多了一間房。

現在的問題

伺服器一增減，mod N 的結果就全盤改變

我們需要一種分配方式，讓新增或移除伺服器時，只影響「鄰近的」資料，而不是全部重算。

🏗️ 把城市畫成一個圓形，每個警察局負責「自己出發、順時針到下一個局」之間的區域。新增一個局，只有附近要重劃；撤掉一個，附近併給下一個——其他地方完全不受影響。

怎麼做：Hash Ring

  1. 把整個 hash 空間排成一個首尾相連的環。
  2. 伺服器名稱算 hash，放到環上的位置。
  3. key 也算 hash，放到環上的位置。
  4. 從 key 的位置順時針走，第一個遇到的伺服器就是負責人。
k1 → 順時針 → s1（負責 k1）
k4 → 順時針 → s0（繞一圈回到 s0）

新增 s4（在 s3、s0 之間）：
  只有原本落在 s4 管轄範圍內的 key 搬移
  其餘 key（k1, k2, k3）完全不受影響

代價

實作比 mod N 複雜：需要維護環上的位置資訊，查找負責伺服器要在環上做搜尋，不是單純的一次取餘數運算。

情境傳統 hash（mod N）Hash Ring
新增一台伺服器幾乎所有 key 重新分配只有相鄰 key 搬移
移除一台伺服器幾乎所有 key 重新分配只有相鄰 key 搬移
實作複雜度極簡單稍複雜

一句話：Hash Ring 把「伺服器增減的影響」從全部縮小到相鄰的一小段弧。

現在的問題

環上點太少，分布很難均勻

Hash Ring 解決了「搬太多」，但伺服器在環上的位置是由 hash 值決定的，不保證均勻分布。只有 3 台伺服器時，很容易出現一台佔環上 70%、另一台只佔 10% 的情況。

兩個具體問題

  1. 弧長不均等：伺服器位置隨機落在環上，管轄範圍可能天差地遠。
  2. Key 分布偏斜：就算弧長差不多，key 的 hash 值也可能天然集中在某一段。

代價：熱點問題（Hotspot）

某台伺服器承受不成比例的大量請求，其他台幾乎閒置。熱點伺服器容易先崩潰，一崩潰它負責的 key 又全部打到資料庫，引發連鎖故障。

一句話：環上的點太稀疏，隨機性不夠，就會有伺服器過載、有伺服器閒置。

現在的問題

怎麼讓環上的點分布得更均勻？

解法很直覺：讓每台伺服器在環上放更多個點，稀疏就變密集，分布自然趨近均勻。

🏗️ 連鎖超商不是只在城市裡開一家店，而是在各行政區都開分店。分店越多，每個區域到最近分店的距離就越平均。

怎麼做：Virtual Nodes（虛擬節點）

每台實體伺服器在環上放置多個虛擬節點，各自對應不同的 hash 位置：

實體伺服器 s0 → 虛擬節點：s0_0, s0_1, s0_2
實體伺服器 s1 → 虛擬節點：s1_0, s1_1, s1_2

key 找到的第一個虛擬節點，對應到那台實體伺服器。實務上通常每台放 100～200 個虛擬節點，是均勻度與管理成本的折衷點。

代價

  1. 需要記錄「虛擬節點 → 實體伺服器」的映射，資料量隨節點數增加。
  2. 查找負責伺服器要在更多點之間搜尋，查找成本略微上升。

伺服器增減時，因為每台伺服器的虛擬節點分散在環的各處，影響會被打散到多台伺服器，而不是集中在相鄰那一台。

一句話：虛擬節點把「一台伺服器」拆成環上的多個代理點，分布均勻，增減的衝擊也被分散掉。

自我檢查

用自己的話解釋看看

為什麼傳統 hash mod N 在伺服器數量改變時會造成大規模快取失效？

因為 N 一變，幾乎每個 key 算出來的 mod 結果都不同，導致原本快取的 key 全部對應到「新」的伺服器，等於瞬間全部快取未命中。

Hash Ring 為什麼能把伺服器增減的影響限制在一小段範圍？

因為伺服器和 key 都固定在環上的位置，只有「被新增或移除的伺服器所管轄的那段弧」需要重新分配，環上其他地方的對應關係完全不受影響。

已經有 Hash Ring 了，為什麼還需要 Virtual Nodes？

因為 Hash Ring 上只放幾個真實伺服器時，位置是隨機的，弧長可能極不均等，容易出現熱點。Virtual Nodes 讓每台伺服器在環上有多個代理點，稀疏變密集，分布才會真正趨近均勻。
