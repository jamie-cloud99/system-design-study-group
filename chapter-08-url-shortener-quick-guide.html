先看流量形狀

短網址系統・十分鐘快速版

第八章快速導覽・給前端工程師的系統設計讀書會

短網址只有兩件核心工作：建立時保存「短碼 → 長網址」，點擊時查回原網址並讓瀏覽器跳轉。但一個連結建立一次，可能被點擊數萬次，所以讀取路徑會比建立路徑更忙。

[建立] 長網址 → 分配短碼 → 保存對應 → 回傳短網址
[點擊] 短網址 → 查回長網址 → HTTP 302 → [原網站]
假設快速估算
每天建立 1 億筆平均約 1,160 次寫入／秒
讀寫比 10：1平均約 11,600 次讀取／秒
保存 10 年約 3,650 億筆對應關係
平均長網址 100 bytes約 36.5 TB 原文；未含索引及複本
🏗️ 行銷活動把帶參數的網址放進簡訊。短連結方便分享，但活動一爆紅，原本只建立過一次的連結會被大量重複讀取。

現在的問題

3,650 億筆資料，要多少短碼才裝得下？

使用數字與大小寫英文字母，共有 62 種字元。六位短碼只有約 568 億種；七位則約有 3.52 兆種，足以容納估算筆數。

唯一 ID → Base62

先領不重複的整數 ID，再換成 62 進位短碼。Base62 是編碼，不是雜湊或加密；只要 ID 唯一且不截斷，短碼就唯一。

[ID 分配器] → 125 → [Base62] → 21
                           ↓
                    [短碼 → 長網址]

代價

要管理 ID 分配器；連續碼容易被猜。第七章的 64-bit Snowflake ID 轉 Base62 可能長達 11 字元，不能直接保證七字元。

如果改用長網址雜湊後截短，雖然省去 ID 分配器，仍要處理碰撞與重試。無論選哪一種，資料庫短碼索引都要守住唯一性；Base62 區分大小寫，索引也必須如此。

一句話：「七位有足夠組合」只是容量估算；產碼方法還要保證唯一、控制數值範圍並處理可猜測性。

現在的問題

短碼產生了，對應關係要如何可靠地留下？

建立 API 必須等資料庫提交成功，才能把短網址回傳給前端。連結同時寫入時，資料庫的短碼唯一約束是最後一道防線。

建立流程

  1. 驗證長網址格式，只接受 http/https。
  2. 領唯一 ID，轉成 Base62 短碼。
  3. 儲存 short_code → long_url。
  4. 提交成功後回傳 201 與短網址。

代價

若請求已成功但回應遺失，前端重試可能建立第二個短碼。需要「同一次操作只建立一次」時，加入冪等鍵並以唯一約束保存結果。

🏗️ 使用者按下建立按鈕後遇到網路逾時，畫面不知道是否成功。前端沿用同一個冪等鍵重試，後端就能回傳第一次建立的短網址。

一句話：同一長網址可以有不同短碼；冪等鍵只讓「同一次建立操作」的重試回到同一結果。

現在的問題

使用者點短連結，瀏覽器該怎麼前往原網址？

短連結可能來自簡訊或 QR Code，不一定會進入你的前端應用。伺服器直接回傳 HTTP 重導向與 Location，瀏覽器就會向原網站發出下一個請求。

[瀏覽器] GET /aB39xY7
    ↓
[短網址服務] 查得 https://example.com/campaign
    ↓
302 Found + Location: https://example.com/campaign
    ↓
[瀏覽器] GET https://example.com/campaign

本章選 302

302 表示暫時跳轉。若希望後續點擊仍經過短網址服務，以便記錄事件，可選 302 並明確設定快取標頭。

代價

每次點擊都可能回到服務端，讀取流量較高。若改用 301，瀏覽器可能記住永久跳轉，之後不再請求短網址服務。

一句話：301 減少服務流量；302 較容易逐次觀測。查無短碼回 404，建立時須拒絕不安全的 URL 協定。

現在的問題

熱門短碼反覆查資料庫，怎麼縮短跳轉時間？

把常用的「短碼 → 長網址」放進伺服器端快取。這是快取旁路：先查快取，未命中才查權威資料庫並回填。

讀取路徑

[GET /短碼]
    ↓
[快取] ─ 命中 → 302
    ↓ 未命中
[資料庫]
    ↓
回填快取 → 302

代價

快取失效時要受控地回退資料庫；大量熱門短碼同時過期，可能造成瞬間回源。剛建立的連結也不能因為讀取複本延遲或舊 404 快取而暫時打不開。

點擊統計可非同步處理，避免分析系統拖慢跳轉。建立 API 可沿用第四章的限流器；公開連結也要考慮惡意網址與掃碼，但限流不能誤傷多人共用的熱門連結。

一句話：快取加速的是讀取，資料庫仍是真相；故障時先保住跳轉，再依業務需求處理統計完整性。

自我檢查

用自己的話解釋看看

為什麼「七位 Base62 足夠」不代表 Snowflake 產出的短碼一定是七位？

七位是依預估總筆數算出的容量；Snowflake 本身是 64-bit 整數，數值可能超過 62 的七次方，轉成 Base62 就會超過七位。若七位是硬需求，發號範圍也必須受限制。

前端建立請求逾時後重試，怎麼避免產生兩個連結？

同一次使用者操作沿用同一個冪等鍵。後端把鍵與建立結果一起保存，重試時回傳第一次的短網址；使用者明確再建立一次才換新鍵。

選 301 或 302，對點擊統計有什麼影響？

301 是永久跳轉，客戶端可能記住結果，後續點擊不再經過短網址服務；302 配合合適快取標頭，較容易觀測每次請求，但服務必須承擔讀取流量。
