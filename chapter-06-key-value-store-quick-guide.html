兩分鐘 Recap

Key-Value Store 十分鐘快速版

你已經用過它了——只是不知道它叫這個名字。

你在瀏覽器打過這行字：

localStorage.setItem("token", "abc123")

單機版本長這樣：

Client → Memory / Hash Map → Disk

這篇快速版只建立三個現實前提，接下來每個技術都是為了解決它們：

現實限制意思
資料會多到一台放不下需要把資料分散到多台機器
機器一定會故障單獨一份資料不安全
網路可能延遲或中斷機器之間的溝通不可靠

現在的問題

一台機器放不下，怎麼辦？

怎麼做

用一致性雜湊（Consistent Hashing）把 key 分散放到多台節點，每台只負責環上的一段範圍。

代價

資料位置變得不直覺，需要額外的路由邏輯才能找到 key 存在哪台機器。

一句話：放不下就分開放，但要有規則知道「誰放哪裡」。

現在的問題

分片之後，一台機器壞了資料就沒了

怎麼做

複製（Replication）：同一份資料存到好幾台機器，其中一台掛了，其他台還在。

代價

多了好幾份副本，寫入要通知的機器變多，也產生了「這幾份會不會不一樣」的新問題。

Client 寫入 → Replica A ✓ Replica B ✓ Replica C（延遲中）

一句話：多存幾份換來不怕故障，但換來「這幾份要不要一樣」的新麻煩。

現在的問題

副本之間要多「一致」？

怎麼做

寫入時等幾份副本確認，讀取時就問幾份副本。重點是讓讀取的人至少碰到一個剛剛寫過的人。這套規則叫 Quorum，才會用 N、W、R 三個數字表示；它的公式是 W + R > N。

代價

W、R 設得越高，讀寫越慢；設得越低，越快但可能讀到舊資料——這就是 CAP（Consistency vs. Availability）取捨。

一句話：讀取的人至少要碰到一個寫過的人，資料才靠得住。

現在的問題

兩個人同時改同一筆資料，誰對？

怎麼做

先替每個版本留下「它經過哪些修改」的紀錄。一個版本包含另一個版本的全部修改時，它就是新版；兩邊各有不同修改時，就標記成衝突。這份版本紀錄叫向量時鐘（Vector Clock）。

代價

系統無法自動判斷誰對，衝突要交給應用層合併，或讓使用者選擇。

一句話：如果兩份版本互相都有對方沒看過的修改，代表它們是同時改出來的，不能亂選一個當贏家。

現在的問題

節點掛了，系統怎麼知道？掛了之後又怎麼補回資料？

怎麼做

  1. 先知道誰沒回應：機器互相交換近況，不需要一台中央監控。Gossip
  2. 暫時請別台代收：等故障機器回來，再把資料還給它。Hinted Handoff
  3. 只補不同的部分：先比摘要，再找出真正不同的資料區塊。Merkle Tree

代價

去中心化偵測需要幾輪傳播才能讓全部節點知道；代收機制和差異同步都增加了系統的實作複雜度。

一句話：沒有老大盯著大家，靠互相閒聊抓故障；代班的人先頂著，回來後再把東西還回去。

現在的問題

資料真的要落到硬碟時，怎麼兼顧寫入快跟讀取快？

怎麼做

  1. 先記一筆：把寫入追加到日誌，避免當機後完全遺失。Commit Log
  2. 先在記憶體整理：累積一批資料並排好順序。MemTable
  3. 再整批寫進硬碟：減少硬碟到處跳著寫。SSTable / LSM-Tree
  4. 讀取先排除：先跳過一定沒有目標 key 的檔案。Bloom Filter

代價

硬碟上會累積很多份 SSTable，需要額外的整理（compaction）程序，讀取有時要查好幾層才找到資料。

Commit Log → MemTable → Bloom Filter → SSTable

一句話：硬碟只做連續寫入，讀取靠 Bloom Filter 先排除掉一定沒有的地方。

自我檢查

用自己的話回答三題

為什麼一致性雜湊解決了容量問題，卻帶來新的風險？

因為資料只分散到多台機器，但每筆資料還是只有一份——任何一台機器故障，那份資料就永久遺失，所以還需要複製。

為什麼資料有副本之後，系統反而多了一個問題？

因為多台機器上的同一筆資料可能不是同一個版本——寫入到達各副本的時間不同，讀取時可能問到還沒更新的那一台。

節點故障後，系統怎麼把缺失的資料補回來？

短暫故障靠 Hinted Handoff：健康節點先代收資料，故障節點恢復後再還回去。長時間故障靠 Merkle Tree：用一層層 hash 比對快速找出差異區塊，只同步不一樣的部分，不用整份資料重新比對。
