先估算規模

通知系統・互動講義

第十章・給前端工程師的系統設計讀書會・可在現場一邊討論一邊操作

通知系統是一條管線：事件發生，查出要通知誰、怎麼通知，再交給第三方送出。送一則很簡單，難的是可靠：第三方會失敗、會變慢，使用者不想被重複打擾，而且一個渠道出事不能拖垮其他渠道。

先看全貌

一則通知會經過哪些元件？

選一種情境，用「下一步」讓小圓點帶你走完。六種情境包含理想送達、退訂、暫時失敗、已知重複，以及入隊前當機與回應遺失。先預測結果，再按下一步驗證。

現在的問題

一個渠道出事，會不會拖垮全部？

假設簡訊服務商掛了。比較「所有通知共用一條佇列」和「每個渠道一條佇列」，按「下一輪」觀察。此示範假設每輪每個 Worker 取一則、失敗簡訊留在隊首；共用模式只有一個 Worker。真實佇列的重試與排程可能不同。

拆出狀態，再用佇列隔離

把資料庫與快取從通知伺服器拆出，伺服器變成可水平擴展的無狀態服務。再用訊息佇列切開「收到請求」與「真的送出」，每個渠道一條佇列、各自的 Worker，也能各自擴充。

代價

多了佇列要維運，通知也不再同步送出，呼叫端拿到的多半只是「已收件」而不是「已送達」（我的推論，書中未明說）。

一句話：獨立佇列與 Worker 降低跨渠道阻塞；共用資料庫、運算資源或第三方配額仍可能互相影響。

現在的問題

送失敗要重送，重送又會重複

書中不保證恰好一次。拖動滑桿比較重複投遞與去重；這個簡化示範假設第一次發送成功且完成紀錄已可靠保存，後續依序投遞，並無並行競爭。「見過」不代表「已送完」；回到上方「回應遺失」情境，觀察本地紀錄無法判定的情況。

3

三道保險

  1. 通知紀錄：保存通知意圖，並有恢復入隊機制。「不漏」的實務目標是不靜默遺失，不保證每則都能顯示。
  2. 重試：依錯誤與期限判斷重試；超過上限留下狀態並告警或人工處理。
  3. 去重：辨識已完成的發送，並以原子操作協調處理權。粒度依事件、收件者、渠道與目標決定；重試沿用識別值。

代價

去重要多查一次儲存。書中沒說去重資料存在哪、怎麼過期，資料會持續成長是我的推論。去重只能減少重複，所以通知內容最好本身就能容忍重複。

實務補充：紀錄與入隊之間仍有當機缺口

只先寫紀錄，當機後仍可能永遠沒入隊。交易式寄件匣（Transactional Outbox）在同一筆資料庫交易保存通知意圖與待發布資料，由背景程序掃描、重試入隊。入隊成功後、標記前當機仍可能重複發布，消費端仍需去重。

[交易：通知意圖＋待發布資料]
          ↓ 提交成功
[背景掃描、重試] → [佇列] → [Worker]
實務補充：逾時與去重能保證到哪裡？

先標記完成再發送，當機可能漏送；發送後才標記，當機可能重送。第三方接受後回應遺失，Worker 只能記為結果未知。要看第三方是否有適用的冪等或查詢能力，本地去重不能保證外部發送恰好一次。

去重鍵可從「事件＋收件者＋渠道＋目標裝置」討論，再由產品規則決定。只用全域事件 ID，可能擋掉其他收件者或裝置的合法通知。

補充（非書中）：重試的等待時間為什麼常常越拉越長？

書中沒有給重試次數或間隔。這是實務上的常見做法：第三方剛恢復時，如果所有失敗的訊息同時重試，又會把它壓垮，所以間隔逐步加長（指數退避）。下圖的秒數是示範用設定，不是 FCM 建議值；實際等待時間以第三方規定為準。無效 token 之類的錯誤重試也沒用。

一句話：重複無法根絕，所以用事件 ID 在送出之前盡量擋掉。

現在的問題

送得可靠了，但使用者被轟炸、不想收的也收到

尊重使用者

  1. 使用者設定：設定表有 user_id、channel、opt_in 三個欄位，每次送出前都檢查。
  2. 限流：限制單一使用者收到的通知數量，否則使用者可能乾脆全部關閉（呼應第四章）。
  3. 範本：預先排好版、帶參數的格式（如補貨通知填入商品名與日期，附追蹤連結）。好處是格式一致、減少錯誤、省時間。
  4. 安全性：推播 API 用 appKey／appSecret 驗證可信任的呼叫端。appSecret 必須留在伺服器端，不能嵌入瀏覽器或散布給使用者的 App；前端經自己的後端與使用者授權流程發起請求。

代價

每則通知多一次設定查詢，設定放快取就要面對過期：使用者剛關掉卻還收到（這是我的推論）。限流太緊也可能擋掉重要通知；驗證碼這類通知要不要獨立優先級，書中沒談，是延伸討論。

細節：監控與事件追蹤

監控佇列長度：書中最關鍵的指標是佇列裡等待的通知數，積壓增加要先找瓶頸。實務上也看最舊訊息等待時間、發送延遲、失敗率、限流率與重試量。Worker 容量不足才擴充；第三方限流時要降速與分批，加 Worker 可能增加錯誤。事件追蹤：接上分析服務，追蹤開啟率、點擊率與互動程度，用來改進策略。

一句話：能送出不代表該送出；信任一旦被打擾消耗掉，就很難換回來。

接上現實

真實系統怎麼取捨？

書中點名的第三方：推播用 APNs 與 FCM，簡訊用 Twilio、Nexmo，Email 用 SendGrid、Mailchimp。各家的限制與重試規則不同，實作前請以官方文件為準。書中沒有指定佇列技術、重試次數與限流門檻，本頁出現的次數與秒數都是示範用設定。

實務補充的官方來源（2026-11-06 核對）

MDN PushManager（權限與訂閱）、Apple APNs（送達限制）、AWS Transactional Outbox（雙寫缺口）、FCM 錯誤碼（重試分類）。完整官方連結見同名 Markdown 講義的來源段落。本頁不載入外部資源。

一句話：自己的系統負責「送給誰、送幾次、失敗怎麼辦」，最後一哩路交給第三方。

自我檢查

面試模擬

為什麼每個渠道要用獨立的佇列？

降低跨渠道阻塞，並各自擴充 Worker；共用資料庫、運算資源與第三方配額仍可能互相影響。

為什麼推播 API 要用 appKey／appSecret？

驗證可信任的呼叫端，避免冒用。appSecret 必須留在伺服器端，不能嵌入瀏覽器或使用者的 App。

怎麼避免使用者收到重複通知？

辨識已完成的發送，依事件、收件者、渠道與目標定義粒度。逾時可能是結果未知，本地去重不能保證外部發送恰好一次。

第三方服務掛了，通知會不會遺失？

保存通知意圖，還要有恢復入隊機制，例如 Outbox。依錯誤與期限重試；過期、永久失敗與超過上限都要記錄，必要時告警或人工處理，不靜默遺失。

（延伸，非書中）行銷通知和驗證碼要不要共用佇列？

不要。大量行銷通知會把驗證碼擋在後面。依優先級分開佇列與 Worker。

讀書會討論題

換個情境，你會怎麼判斷？

使用者關掉行銷通知卻還收到，查哪裡？

檢查發送前設定查詢、快取更新與是否有入口繞過檢查。排隊期間可能退訂，要送前再查；已交第三方的通知不一定能撤回。

週年慶推播給 500 萬人，哪裡有壓力？

通知服務處理請求，佇列吸收突發；Worker 仍受第三方配額限制。分批與優先級要避免活動通知擋住即時通知。

同一筆出貨通知收到三次，怎麼查？

追查上游重複、發送結果未知後重試，或多台裝置的合法發送。去重粒度依事件、收件者、渠道與目標定義，同一次重試沿用識別值。

簡訊商維護兩小時，哪些通知能等？

行銷可延後；驗證碼須檢查期限與已授權的替代渠道，過期就停止發送並記錄。不能假設所有通知都能自動換渠道。
