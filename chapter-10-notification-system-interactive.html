先看規模

通知系統・互動講義

第十章・給前端工程師的系統設計讀書會・可在現場一邊討論一邊操作

通知系統是一條管線：事件發生，查出要通知誰、怎麼通知，再交給第三方送出。送一則很簡單，難的是可靠：第三方會失敗、會變慢，使用者不想被重複打擾，而且一個渠道出事不能拖垮其他渠道。

使用者安裝 App 或註冊時，API 伺服器把聯絡資訊存進資料庫：使用者表放 Email 與手機號碼，裝置表放裝置 token。一個使用者可有多台裝置，所以一則推播能送到全部。

先看全貌

一則通知會經過哪些元件？

選一種情境，用「下一步」讓小圓點帶你走完。四種結局：成功送達、使用者關閉通知而被丟棄、第三方失敗後重試成功、重複訊息被去重丟棄。

一句話：通知系統的每個元件都在回答：該不該送、送去哪、送失敗怎麼辦。後面幾節逐一拆開。

現在的問題

一個渠道出事，會不會拖垮全部？

假設簡訊服務商掛了。比較「所有通知共用一條佇列」和「每個渠道一條佇列」，按「下一輪」觀察。每輪每個 Worker 取一則；簡訊永遠送不出去。

拆出狀態，再用佇列隔離

把資料庫與快取從通知伺服器拆出，伺服器變成可水平擴展的無狀態服務。再用訊息佇列切開「收到請求」與「真的送出」，每個渠道一條佇列、各自的 Worker，也能各自擴充。

代價

多了佇列要維運，通知也不再同步送出，呼叫端拿到的多半只是「已收件」而不是「已送達」（我的推論，書中未明說）。

一句話：佇列不只用來緩衝，也用來把故障關在自己的渠道裡。

現在的問題

送失敗要重送，重送又會重複

書中的答案是：不保證恰好一次，分散式系統偶爾會出現重複。做法是去重：事件進來時檢查事件 ID，見過就丟棄，沒見過才送。書中也說這只能減少重複，不能完全消除。拖動滑桿決定同一則訊息被投遞幾次，再切換去重。

3

三道保險

  1. 通知紀錄：書中原則是通知可以延遲、可以亂序，但絕不能遺失，所以存進通知紀錄資料庫。
  2. 重試：送失敗放回佇列，重試預先設定的次數，持續失敗就通知開發者。
  3. 去重：以事件 ID 檢查是否處理過。

代價

去重要多查一次儲存。書中沒說去重資料存在哪、怎麼過期，資料會持續成長是我的推論。去重只能減少重複，所以通知內容最好本身就能容忍重複。

補充（非書中）：重試的等待時間為什麼常常越拉越長？

書中沒有給重試次數或間隔。這是實務上的常見做法：第三方剛恢復時，如果所有失敗的訊息同時重試，又會把它壓垮，所以間隔逐步加長（指數退避）。下圖的秒數是示範用設定；無效 token 之類的錯誤重試也沒用。

一句話：重複無法根絕，所以用事件 ID 在送出之前盡量擋掉。

現在的問題

送得可靠了，但使用者被轟炸、不想收的也收到

尊重使用者

  1. 使用者設定：設定表有 user_id、channel、opt_in 三個欄位，每次送出前都檢查。
  2. 限流：限制單一使用者收到的通知數量，否則使用者可能乾脆全部關閉（呼應第四章）。
  3. 範本：預先排好版、帶參數的格式（如補貨通知填入商品名與日期，附追蹤連結）。好處是格式一致、減少錯誤、省時間。
  4. 安全性：推播 API 用 appKey／appSecret 驗證，只有通過驗證的用戶端能呼叫。

代價

每則通知多一次設定查詢，設定放快取就要面對過期：使用者剛關掉卻還收到（這是我的推論）。限流太緊也可能擋掉重要通知；驗證碼這類通知要不要獨立優先級，書中沒談，是延伸討論。

細節：監控與事件追蹤

監控佇列長度：書中最關鍵的指標是佇列裡等待的通知數，積壓變大代表處理太慢，要加 Worker。事件追蹤：接上分析服務，追蹤開啟率、點擊率與互動程度，用來改進策略。

一句話：能送出不代表該送出；信任一旦被打擾消耗掉，就很難換回來。

接上現實

真實系統怎麼取捨？

書中點名的第三方：推播用 APNs 與 FCM，簡訊用 Twilio、Nexmo，Email 用 SendGrid、Mailchimp。各家的限制與重試規則不同，實作前請以官方文件為準。書中沒有指定佇列技術、重試次數與限流門檻，本頁出現的次數與秒數都是示範用設定。

一句話：自己的系統負責「送給誰、送幾次、失敗怎麼辦」，最後一哩路交給第三方。

面試模擬

為什麼每個渠道要用獨立的佇列？

隔離故障。某個第三方變慢或失敗，只會堆積自己的佇列，其他渠道照常運作；各渠道也可以獨立擴充 Worker 數量。

為什麼推播 API 要用 appKey／appSecret？

防止任何人冒用我們的系統發通知。只有通過驗證的用戶端才能呼叫。

怎麼避免使用者收到重複通知？

書中的答案是無法保證恰好一次，所以用事件 ID 去重：事件進來先檢查，見過就丟棄。這只能減少重複，不能完全消除。

第三方服務掛了，通知會不會遺失？

書中原則是通知可以延遲、亂序，但不能遺失：存進通知紀錄資料庫，失敗時放回佇列重試預先設定的次數，持續失敗就通知開發者。

（延伸，非書中）行銷通知和驗證碼要不要共用佇列？

不要。大量行銷通知會把驗證碼擋在後面。依優先級分開佇列與 Worker。
